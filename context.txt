React Frontend
↓
HTTPS / REST APIs
↓
Reverse Proxy / API Gateway where justified
↓
Spring Boot Backend
↓
Application and Domain Modules

# PART 6: ENTERPRISE DOCUMENT MANAGEMENT ENGINE

Treat document management as the core business capability.

## 6.1 Document ingestion

Implement a robust document ingestion lifecycle.

Support:

- Single uploads.
- Multiple uploads.
- Bulk upload.
- Large-file upload.
- Resumable uploads where justified.
- Upload progress.
- File validation.
- MIME verification.
- Filename sanitisation.
- File-size limits.
- Extension restrictions.
- Duplicate detection.
- Content integrity.
- Malware scanning.
- Metadata extraction.
- Document classification.
- Storage.
- Processing status.

Use temporary upload states where necessary.

Never trust filenames or content-type headers supplied by clients.

Consider content-based validation and secure file handling.

## 6.2 Document storage

Use an object-storage abstraction.

Evaluate MinIO or another S3-compatible provider.

Store structured document information in MySQL and binaries in object storage.

Support:

- Unique storage keys.
- Checksums.
- Storage metadata.
- Version-aware object references.
- Secure access.
- Retention.
- Archival.
- Recovery.
- Storage-provider abstraction.

Implement short-lived presigned URLs for large uploads and downloads where appropriate.

The backend must authorise the operation before issuing access.

Do not expose permanent public URLs or internal storage paths.

Implement consistency safeguards between database records and stored objects.

Account for partial failures where a storage operation succeeds but a database transaction fails, or vice versa.

Use suitable compensation, reconciliation and cleanup mechanisms.

## 6.3 Document processing pipeline

Introduce asynchronous processing where beneficial.

Evaluate:

- Apache Tika.
- Tesseract OCR.
- ClamAV.
- LibreOffice headless.
- RabbitMQ.
- Background workers.

A suitable processing lifecycle could be:

Uploaded → Pending Validation → Scanning → Processing → Extracting Metadata → Indexing → Available.

Also support:

- Processing failure.
- Retry.
- Dead-letter handling.
- Manual reprocessing.
- Processing history.
- Duplicate job prevention.
- Idempotency.

Do not perform expensive OCR, conversion or indexing synchronously inside normal upload requests.

## 6.4 Document metadata

Support:

- Standard metadata.
- Custom metadata.
- Document types.
- Categories.
- Tags.
- Ownership.
- Department.
- Author.
- Creation date.
- Effective date.
- Expiry date.
- Classification.
- Confidentiality.
- Retention category.
- Custom attributes.

Where appropriate, support configurable metadata schemas associated with document types.

Validate metadata according to its configured schema.

## 6.5 Folder and taxonomy management

Implement:

- Hierarchical folders.
- Nested folders.
- Document categories.
- Tags.
- Departments.
- Document collections.
- Custom taxonomies.
- Folder-level permissions.
- Bulk organisation.
- Saved filters.

Avoid designing a folder hierarchy that becomes unnecessarily restrictive.

Allow documents to be discovered through metadata, tags and search even when their physical organisation is complex.

## 6.6 Document versioning

Implement a proper version-control mechanism.

Support:

- Automatic revision creation.
- Version numbering.
- Version history.
- Version comments.
- Revision attribution.
- Previous-version retrieval.
- Version restoration.
- Change timestamps.
- Historical integrity.
- Concurrent modification handling.

Never silently overwrite an existing document revision.

Define clear rules for the relationship between the logical document and its physical stored versions.

## 6.7 Check-in/check-out

Consider:

- Check-out.
- Check-in.
- Editing locks.
- Lock ownership.
- Lock expiration.
- Lock renewal.
- Administrative release.
- Concurrent modification detection.

Prevent accidental overwriting and uncontrolled concurrent editing.

Evaluate:

- Secure login.
- Password hashing.
- Account verification.
- Password reset.
- MFA.
- Session expiration.
- Token management.
- Refresh-token rotation if applicable.
- Session revocation.
- Account lockout.
- Login monitoring.
- Logout.
- Identity-provider integration.

Select an appropriate authentication model.

Do not store access tokens insecurely in browser local storage without a justified security assessment.

Consider secure HttpOnly cookies and appropriate CSRF protections where suitable.

## 8.2 Authorisation

Potential roles:

- Super Administrator.
- Organisation Administrator.
- Department Administrator.
- Document Administrator.
- Document Owner.
- Document Editor.
- Reviewer.
- Approver.
- Read-only User.
- External Collaborator.

Support permissions at appropriate levels:

- Tenant.
- Organisation.
- Department.
- Folder.
- Document.
- Individual action.

- View.
- Upload.
- Download.
- Edit.
- Delete.
- Share.
- Approve.
- Reject.
- Archive.
- Restore.
- Manage permissions.

## 8.3 Multi-tenancy

Design ManageEDocs to support multiple independent organisations.

Consider:

- Tenant identification.
- Tenant-scoped repositories.
- Tenant-aware authentication.
- Tenant-specific roles.
- Tenant-level settings.
- Tenant-aware storage.
- Tenant-aware search.
- Tenant-specific audit records.

- Tenant-specific retention.
- Tenant isolation.

Never rely on an untrusted tenant ID supplied by the frontend.

Ensure background workers, scheduled tasks, exports, reports and search queries respect tenant boundaries.

Choose the appropriate isolation model based on requirements and document the trade-offs.

- XSS.
- CSRF.

- IDOR.

- Weak session management.
- Excessive permissions.
- Insecure sharing.

## 18.4 End-to-end acceptance scenarios

### Scenario A: Document upload

A user logs in, uploads a document, receives upload feedback, the backend validates it, stores it, creates its metadata, initiates processing and makes it available.

### Scenario B: Document retrieval

An authorised user searches for a document, filters results, opens its details, previews it and downloads it.

### Scenario C: Access control

A restricted user attempts to access another user's document. The backend rejects the operation and records the relevant security event.

### Scenario D: Version management

A user uploads a revision, the system creates a new version, preserves the old version and allows authorised retrieval of previous versions.

### Scenario E: Approval workflow

A document is submitted, assigned to a reviewer, reviewed, approved or rejected, and its status and history are updated correctly.

### Scenario F: Multi-tenancy

A user from one organisation attempts to access another organisation's documents, metadata, search results or reports. The system prevents cross-tenant access.

### Scenario G: Document retention

A document reaches its retention deadline. The system evaluates the policy, checks legal holds and performs the appropriate archival or disposal action.

### Scenario H: Processing failure

A document-processing job fails. The system records the failure, supports retries and does not corrupt the underlying document record.

### Scenario I: Recovery

The system is restarted and recovers correctly without losing committed document records or creating inconsistent processing states.
